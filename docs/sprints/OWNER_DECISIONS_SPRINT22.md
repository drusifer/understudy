42. (2026-11-05) A play and a scene: the **play** is the one file type, the outermost configuration of an automation, and a play can call another play (`do: { play: x.yaml }`) to reuse logic already known to work; "scene" names a play's body (its beats), not a second file type. **The stage is the play's interface (its API):** it declares every prop (the typed declarations that `inputs:` held; no `inputs:` or `props:` section), every piece it reads (`kind: file`) and every piece it writes (`kind: file, access: write`). **Running a play means providing its stage.** From the command line: props from `--with`, read pieces from files on disk (`path:` is only a default for this case), write pieces as files in the run folder. Called from a play: the call's `with:` binds each prop and read piece to the caller's values and pieces, and each write piece to a piece of the caller, which receives the rows (appended per row under `each`); a called play never touches the disk. This removes `outputs:` on a final beat and the `{input, output}` pairs and their `unpair` beats; what a called play writes carries its own keys. The owner rejected the alternative of returning a called play's written files to the caller ("the written files thing is really part of the set").
